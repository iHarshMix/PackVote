# AI Assistant Workflow Rules for PackVote

Follow these strict rules during the development of this project:

1. **Preserve Original Documentation:** Never delete or overwrite the original text in the main project plan (`plan and docs/packvote_project_plan...`). If a deviation from the technical design occurs (e.g., adding a new DB column or changing a route), append an implementation note using a blockquote format (e.g., `> **Implementation Update (Date):** [Reason for change]`) next to the relevant section.
2. **Track Progress via Checkboxes:** The Build Order in the project plan uses Markdown checkboxes. Whenever you complete a step, you must update the project plan file by changing the empty checkbox (`- [ ]`) to checked (`- [x]`).
3. **Use Scratchpad Artifacts for Micro-tasks:** Do not clutter the main project plan with granular, day-to-day to-dos. When executing a complex step, generate an internal `task.md` artifact to act as your dynamic checklist and scratchpad, checking off micro-tasks as you go.
4. **Strict Git Flow:** Before starting a new step in the Build Order, branch out from `main` (e.g., `git checkout -b feat/step-X-name`). Once the step is complete and verified, commit the code and merge it back into `main` before proceeding to the next step.
5. **Model Switching Recommendations:** When the current model (Gemini 3.5 Flash) is about to perform a task requiring deep reasoning, advanced planning, or complex mathematics (e.g., designing the state machine logic in Step 4 or coding the ranked-choice IRV tiebreak in Step 7), the AI must explicitly recommend that the user temporarily switch the IDE's model selection to a more capable reasoning model (e.g., Gemini 3.1 Pro or another high-reasoning model) for that turn. Once the complex reasoning step is finished, the AI should instruct the user to toggle back to the faster development model (Gemini 3.5 Flash) for active file execution, linting, and testing.
6. **Schema Vector Dimension Sync:** When changing embedding models/providers, always verify that the `.env` `EMBEDDING_DIMENSION` aligns with the model output. If the dimension changes, you must drop the existing tables to prevent psycopg2 dimension mismatch errors. If dropping tables from Python blocks due to database locks, bypass the locks by dropping tables directly inside the container via `docker.exe exec`.
7. **Lazy LLM Factory Imports:** Always import provider-specific LangChain libraries (e.g., `langchain_anthropic`, `langchain_google_genai`) dynamically inside factory functions rather than at the top level of the module. This prevents top-level network or metadata server connection hangs (e.g., GCP metadata lookups) during general test collection or application boot.
8. **LangChain Mock Sequence assertions:** When mocking LLMs/chains in LangChain piped expressions (e.g. `prompt | mock_llm`), the mock behaves as a direct callable under the hood. Set BOTH `mock_llm.invoke.return_value` and `mock_llm.return_value` in unit tests to ensure compatibility.
9. **LangGraph Conditional Edges are Read-Only:** Routing functions passed to conditional edges (e.g., `should_retry`) are evaluation paths, not graph nodes. Any state modifications performed within them are discarded by LangGraph. All state mutations (such as incrementing retry counts or setting flags) must happen inside the preceding state-saving Node.
10. **Streamlit Multi-page State Fallbacks:** When navigating using `st.switch_page`, Streamlit may clear active URL query parameters. Always save key identifiers (e.g., `token`, `trip_id`) to `st.session_state` before switching, and load them using a fallback in the target page (e.g., `token = st.query_params.get("token") or st.session_state.get("token")`).
11. **Post-Test Database Reseeding:** Running the test suite (`pytest`) wipes the `Destination` table and seeds mock data. Always run the seed script `python scripts/seed_destinations.py` after a test run before starting or testing the application locally.
12. **Recommendation Uniqueness Constraint:** Prompt templates recommending travel options must explicitly instruct the LLM to suggest unique and distinct destination names to prevent it from outputting multiple variations of the same destination.
13. **Proactive File Updates:** When completing a step, running verification, or making any code changes, always proactively update **all** related tracking files without waiting to be asked. This includes: checking off build order checkboxes in the project plan, updating `task.md` progress, refreshing the `walkthrough.md` artifact with what was accomplished, and appending implementation notes to the project plan if any deviations occurred. No file should be left stale.
